# USB load measurement, orangepi-z2w, 2026-10-07

## Question

Does the MUSB OTG controller running in PIO mode (musb_sunxi returns no DMA
controller, so the CPU copies every byte between memory and the FIFO) load
the CPU enough to justify adding USB DMA support for the H618?

## What was done

- Kernel source check (6.19.2, `drivers/usb/musb/`): `sunxi_musb_dma_controller_create()`
  returns NULL, so the controller is PIO only. `musbhs_dma_controller_create_noirq()`
  exists in `musbhsdma.c`, but nothing shows the H618 has the Mentor HSDMA
  registers it expects (the Allwinner BSP most likely uses its own
  `sunxi_usb/udc` with the generic DMA engine - unverified, no BSP source at hand).
- Ran `measure-usb-load.sh` on the board during an Android Auto session
  with the desktop head unit (DHU).

## Results

| | Run 1: 25 s, light | Run 2: 498 s, navigation + Gemini voice + Deezer |
|---|---|---|
| Samples | 24 | 483 |
| CPU, whole system, avg / max | 4.9% / 8.6% | 4.2% / 9.5% |
| of which sys | 3.1% | 2.6% |
| of which irq+softirq | 1.0% | 0.8% |
| Busiest core, max | 12.3% | 13.2% |
| musb-hdrc IRQ/s, avg / max | 792 / 2145 | 687 / 2508 |
| aa-proxy-rs (100% = 1 core), avg / max | 5.0% / 11.7% | 4.4% / 12.6% |

No USB reset was reported by the tester during either run.

## Conclusion

CPU load stays low and stable under realistic traffic: the busiest core never
exceeds 13.2%. PIO is not a bottleneck, so USB DMA would at best trim a few
CPU points and the IRQ rate. The DMA lead is dropped; do not port a DMA driver
for this unless a new symptom points at it.
